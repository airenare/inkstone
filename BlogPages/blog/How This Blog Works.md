Every page you read here was written as a plain `.md` file in Obsidian. There is no export step, no CMS, no build pipeline. A small Python server reads the vault directly and serves it as a website. This post is a complete technical walkthrough of how that works — from filesystem walk to rendered HTML.

> [!abstract] What This Covers
> Four-module architecture · Two-pass vault loading · The full markdown pipeline · Routing · Hot-reload · Dataview queries · RSS, sitemap, and search. All with code from the actual source files.

---

## Architecture

The app is split across four modules. The import chain is strictly one-way:

```
config.py  ←  converters.py  ←  posts.py  ←  app.py
```

| Module | Responsibility |
|--------|---------------|
| `config.py` | Loads `.env`, sets `VAULT_PATH`, tag constants, reads `VERSION` |
| `converters.py` | All markdown transformation functions and the `render_markdown()` pipeline |
| `posts.py` | Two-pass vault loader, in-memory post store, hot-reload logic |
| `app.py` | Flask routes, context processor, RSS/sitemap/search endpoints |

`app.py` imports `posts`, never the reverse. `converters.py` knows nothing about Flask or routes. This keeps the boundary between "processing markdown" and "serving HTTP" clean and testable.

## The Two-Pass Load

The vault is loaded in two passes on startup (and again on any file change). The reason for two passes is wiki-link resolution: a post in `/blog` might link to a post in `/gallery` that has not been processed yet. The index has to be complete before any markdown is rendered.

### Pass 1 — Scan and Index

`load_posts()` in `posts.py` walks the entire vault with `os.walk()`. For every `.md` file it finds:

1. Parses YAML frontmatter with PyYAML
2. Resolves the `title` (frontmatter → first H1 → filename)
3. Computes `section` from the folder path relative to the vault root
4. Computes `url_path` from section + slug
5. Adds every note to `dataview_index` (feeds Dataview queries later)
6. If the note has a publish tag (`blog` or `website`), adds its slug to `url_index`

```python
url_index[slugify(title)] = url_path
```

`url_index` is a flat dict: `slugify(title) → url_path`. It is the only thing needed to resolve `[[Wiki Links]]` — the actual rendering happens in Pass 2.

Files without a publish tag still get a `dataview_index` entry. This is how Dataview queries can reference private notes.

### Pass 2 — Render

With `url_index` complete, every candidate file is rendered:

```python
for (filepath, f, metadata, md, tags, title, slug,
     section, url_path) in candidates:

    html, toc = render_markdown(md, filepath, url_index, dataview_index)
    summary = metadata.get("summary") or _make_summary(html)
```

`render_markdown()` returns a `(html_str, toc)` tuple. The `toc` is generated by Python-Markdown's `toc` extension — it is available in templates as `post.toc`.

After rendering, the loader builds a `post_data` dict for each file and routes it to one of three places:

| Destination | Condition |
|-------------|-----------|
| `SECTION_ROUTES[section_url]` | File has `listing` tag — auto-generates a post index |
| `SECTION_ROUTES[section_url]` | File has `homepage` tag — renders its own markdown content |
| `ALL_POSTS[url_path]` | Everything else — a regular published post |

`listing` wins over `homepage` if both are present. Files tagged `listing` or `homepage` do not appear in `ALL_POSTS`.

## URL Structure

Vault folder structure maps directly to URL structure. The `section` is derived from the path of the `.md` file relative to the vault root:

| Vault path | Section | URL |
|-----------|---------|-----|
| `blog/My Post.md` | `blog` | `/blog/My-Post` |
| `gallery/arts/Piece.md` | `gallery/arts` | `/gallery/arts/Piece` |
| `About.md` (root) | `` (empty) | `/About` |
| `blog/Blog Index.md` (tagged `listing`) | `blog` | `/blog` |

Slugs are generated with `slugify()` in `converters.py` — strips punctuation, replaces spaces with hyphens, preserves case. A frontmatter `slug:` field overrides the auto-generated one.

## The Markdown Pipeline

`render_markdown(md, path, url_index, dataview_index)` applies six transformations in order. The order matters — each step assumes the previous ones have already run.

### Step 1 — `strip_leading_h1()`

Removes the first `# Title` line from the body. The post template renders the title from frontmatter, so keeping it in the body would duplicate it.

```python
def strip_leading_h1(md):
    lines = md.split("\n")
    for i, line in enumerate(lines):
        if line.startswith("# "):
            del lines[i]
            break
    return "\n".join(lines)
```

Only the first H1 is removed. Subsequent headings are left alone.

### Step 2 — `convert_media()`

Converts Obsidian media embeds (`![[file.ext]]`) to HTML. The function reads the file line-by-line and applies different logic depending on how embeds are arranged:

- **Multiple embeds on one line** (separated by spaces) → **slider gallery**
- **Single embed on its own line** → added to a **lightbox gallery** buffer
- When a non-embed line is encountered, any buffered lightbox images are flushed as a `<div class="thumb-gallery">`

```python
# Slider: multiple embeds on one line
if len(matches) > 1 and " " in line:
    for filename, caption in matches:
        slider.append(f'<img src="/attachments/{rel}" ...>')
    output.append(flush_slider())

# Lightbox: single embed on its own line
elif len(matches) == 1 and line.strip().startswith("![["):
    gallery.append(f'<img src="/attachments/{rel}" data-gallery="gallery" ...>')
```

Images are resolved against an `_attachments/` subfolder **relative to the note's folder**. A post in `blog/` looks for images in `blog/_attachments/`. Videos (`.mp4`, `.webm`, `.mov`) become `<video>` elements instead of `<img>`.

### Step 3 — `convert_links()`

Converts `[[Wiki Links]]` and `[[Title|Display Text]]` to standard markdown links using the `url_index` built in Pass 1:

```python
def repl(match):
    target = match.group(1).strip()
    display = (match.group(2) or target).strip()
    slug = slugify(target)
    url = url_index.get(slug) if url_index else None
    return f"[{display}]({url or '/' + slug})"
```

If `slug` is not found in the index — because the target is a private note or doesn't exist — the link falls back to `/{slug}`. Navigating to a private note shows a placeholder page rather than a 404.

### Step 4 — `convert_callouts()`

Obsidian callout syntax is not standard markdown. This step converts it to `<div>` blocks:

```
> [!tip] Title
> Content line one
> Content line two
```

→

```html
<div class="callout callout-tip">
  <div class="callout-title">...</div>
  <div class="callout-content">Content line one
Content line two</div>
</div>
```

The parser is line-by-line: it detects the `> [!type] Title` header, accumulates `>` prefixed lines as content, and flushes when a non-`>` line arrives. All standard Obsidian callout types are supported (`note`, `tip`, `info`, `warning`, `danger`, `abstract`, `question`, `success`, `failure`, `bug`, `example`, `quote`).

### Step 5 — `convert_checkboxes()`

Converts Obsidian checkbox lists to HTML with proper nesting. Indentation level (4 spaces per level) determines nesting depth:

```markdown
- [ ] Unchecked parent
    - [x] Checked child
    - [ ] Unchecked child
```

The parser tracks a `stack` of open `<ul>` tags and opens or closes them as the indent level changes. Each checkbox becomes a disabled `<input type="checkbox">` so the visual state is preserved without any interactivity.

### Step 6 — `markdown.Markdown().convert()`

The transformed string is passed to Python-Markdown with five extensions:

| Extension | What it adds |
|-----------|-------------|
| `fenced_code` | ` ```language ` code blocks |
| `tables` | GFM-style pipe tables |
| `toc` | Auto-generated table of contents; returns `md_obj.toc` |
| `md_in_html` | Markdown inside raw HTML blocks |
| `codehilite` | Syntax highlighting via Pygments |

```python
md_obj = markdown.Markdown(
    extensions=["fenced_code", "tables", "toc", "md_in_html", "codehilite"],
    output_format="html5",
)
html_str = md_obj.convert(md)
toc = md_obj.toc if md_obj.toc_tokens else ""
return html_str, toc
```

The `toc` is only returned when the document actually has headings (`md_obj.toc_tokens` is non-empty). Templates receive it as `post.toc` and can render it as a collapsible block.

## Dataview Queries

The engine implements a server-side subset of Obsidian's Dataview plugin. A fenced `dataview` block:

````markdown
```dataview
TABLE file.link AS Title, date AS Date
FROM #blog
WHERE !contains(tags, "listing")
SORT date DESC
```
````

…is parsed and executed against `dataview_index` — the same index built in Pass 1 that contains every `.md` file in the vault, whether published or not.

Supported query features:
- `TABLE` with column expressions and `AS` aliases
- `FROM #tag` filtering
- `WHERE` with `contains()`, `!contains()`, `AND` (`&`), `OR` (`|`)
- `SORT field ASC|DESC`
- `GROUP BY field` with `rows.field` aggregation
- `WITHOUT ID` to suppress the default file link column
- Expression functions: `link()`, `join()`, `list()`

This is how the Books section generates its reading list automatically — no manual curation required.

## Routing

A single Flask catch-all route handles everything:

```python
@app.route("/", defaults={"path": ""})
@app.route("/<path:path>")
def serve(path):
    post_store.maybe_reload()
    url_path = "/" + path if path else "/"

    if url_path in post_store.SECTION_ROUTES:
        # homepage or auto-generated listing
        ...

    if url_path in post_store.ALL_POSTS:
        # regular post
        ...

    if url_path in post_store.PRIVATE_ROUTES:
        # private note placeholder
        ...

    abort(404)
```

`maybe_reload()` is called first on every request (see Hot-Reload below). Then the path is looked up in three dicts in priority order: section routes, published posts, private placeholders.

Special routes are registered separately:

| Route | Handler |
|-------|---------|
| `/attachments/<path>` | `send_from_directory(VAULT_PATH, path)` |
| `/feed.xml` | Hand-rolled RSS 2.0 XML, latest 20 posts |
| `/sitemap.xml` | All `SECTION_ROUTES` + `ALL_POSTS` URLs |
| `/search` | Full-text + label filter across `ALL_POSTS` |
| `/label/<label>` | Archive page for a single content label |

Nav links are auto-generated from top-level `SECTION_ROUTES` keys (direct children of `/`). Posts with `menu_order` in their frontmatter are additionally pinned to the nav — this is the intended mechanism for standalone pages like About or Contact.

### Auto-listing

If a folder contains published posts but has no explicit `listing`-tagged file, a listing route is generated automatically:

```python
for post_data in all_posts.values():
    section_url = post_data["section_url"]
    if section and section_url not in section_routes:
        # synthesise a listing route for this section
        section_routes[section_url] = {"type": "listing", ...}
```

This means you can drop notes into a new folder and get a working section listing without creating an index file.

## Hot-Reload

`maybe_reload()` is designed to be called on every HTTP request with near-zero cost in the common case:

```python
def maybe_reload():
    if not _reload_lock.acquire(blocking=False):
        return  # another thread is already reloading

    try:
        newest = 0
        for root, _, files in os.walk(VAULT_PATH):
            for f in files:
                newest = max(newest, os.path.getmtime(...))

        if newest > LAST_SCAN_TIME:
            (ALL_POSTS, ...) = load_posts()
            LAST_SCAN_TIME = newest
    finally:
        _reload_lock.release()
```

The lock is non-blocking: if a reload is already in progress on another thread, the current request skips the check and serves the existing (slightly stale) data. This prevents reload storms under concurrent traffic.

The cost when nothing has changed is one `os.walk()` with `os.path.getmtime()` per file. On a small vault this is imperceptible. The full `load_posts()` is only triggered when `newest > LAST_SCAN_TIME`.

The practical effect: edit a note in Obsidian, save it, refresh the browser. The change is live. No restart, no rebuild, no deploy.

## Private Notes

Every `.md` file in the vault gets a `dataview_index` entry and a computed URL — even unpublished notes. Navigating to a private note's URL shows a placeholder page (`private.html`) rather than a 404:

```python
if url_path in post_store.PRIVATE_ROUTES:
    entry = post_store.PRIVATE_ROUTES[url_path]
    return render_template("private.html", entry=entry, back_url=back_url)
```

This matters for wiki-links: if you link to a private note, the link renders as a valid anchor. Clicking it shows the placeholder rather than a broken page. This mirrors Obsidian's own behaviour where linked-but-not-published notes are still reachable.

## The Post Dict

Every post, whether homepage, listing, or regular, is stored as a plain dict. The fields available in templates:

| Field | Source |
|-------|--------|
| `title` | Frontmatter → H1 → filename |
| `date` | Frontmatter `date:`, normalised to `datetime` |
| `html` | Rendered body HTML |
| `toc` | Table of contents HTML string (empty if no headings) |
| `summary` | Frontmatter `summary:` or first 200 chars of plain text |
| `reading_time` | `max(1, word_count // 200)` — minutes |
| `labels` | Sorted, lowercased list from frontmatter `labels:` |
| `featured` | `True` if `featured` tag is present |
| `priority` | Integer sort key for featured ordering |
| `banner` | URL string, or `None` |
| `banner_x` / `banner_y` | Float 0–1, CSS `background-position` focal point |
| `url_path` | Canonical URL path |
| `section` | Folder path relative to vault root |
| `back_url` | Parent section URL for the ← Back link |

## Frontmatter Reference

```yaml
---
tags:
  - blog        # required to publish (or "website")
  - featured    # shows in the Featured section of the parent listing
  - homepage    # renders this file's content at the section root URL
  - listing     # auto-generates a post index at the section root URL
  - search      # root homepage only: adds Search to the top nav
date: 2026-01-20
title: My Post
slug: my-post            # optional; auto-generated from title if omitted
priority: 0              # featured sort order; 0 = first; date breaks ties
summary: "..."           # listing card text; auto-derived if omitted
banner: "https://..."    # banner image URL
banner_x: 0.5            # horizontal focal point (0 = left, 1 = right)
banner_y: 0.4            # vertical focal point (0 = top, 1 = bottom)
menu_order: 1            # pin to top nav; lower = further left
labels:
  - python
  - obsidian
---
```

`tags` are reserved engine keywords — they change how the server handles the file. `labels` are for readers — they appear as clickable badges on the post page and drive the label filter on the search page and `/label/<name>` archive pages.

> [!warning] Colons in frontmatter values
> YAML uses `: ` (colon + space) as a key-value separator. If your `title`, `summary`, or any other string field contains a colon, you must wrap the entire value in double quotes — otherwise the YAML parser silently turns it into a nested dict and the post's URL, title, and wiki-links all break.
> ```yaml
> title: "From Vault to Web: How This Blog Works"   # correct
> title: From Vault to Web: How This Blog Works      # broken
> ```
> The engine will log a warning to stderr and fall back to the H1 heading or filename when it detects this, so the post still loads — but the title will be wrong until you add the quotes.
